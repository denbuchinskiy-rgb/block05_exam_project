Паспорт диплома 
Тема: AI-платформа для малого бизнеса (Интернет-магазин): аналитика, прогнозирование и чат-интерфейс 
Проблема: построить воспроизводимую модель регрессии для прогноза quantity и снизить долю ручной обработки данных.
Пользователь: менеджер продаж / категорийный менеджер.
Объект прогноза: количество единиц товара в строке продажи при заданных price, discount, manager, city, category, product.
Вход: числовые price, discount; категориальные manager, city, category, product; при наличии — дата.
Выход: прогноз quantity; метрики на test; сравнение с baseline; warning об ограничениях.
Метрики: MAE, RMSE, R²; дополнительно WAPE/MAPE с оговоркой; сравнение с DummyRegressor.
Контроль: 80/20; при наличии времени — хронологический split; CV только в train; test — один раз.
Модели: baseline, Ridge/LinearRegression, RandomForest, HistGradientBoosting; подбор гиперпараметров по CV.
Технологии: Python, Pandas, NumPy, Matplotlib, scikit-learn, joblib, pytest, Streamlit, Git/GitHub.
Ограничения: модель не causal; не заменяет прогноз спроса с учётом остатков и сезонности; ненадёжна для новых категорий и выбросов.
Краткий вердикт
	Паспорт проекта в целом корректный и реализуемый, но для дипломного проекта ему не хватает важных деталей: гранулярности и горизонта прогноза, стратегии split с учётом времени/групп, определения baseline, обработки категориальных признаков и утечек, бизнес-метрик и формализованных ограничений. Особенно спорно поле «Пользователь: конечный потребитель» — прогноз quantity проданных единиц обычно нужен не конечному потребителю, а менеджеру/аналитику/категорийному менеджеру.

Критические пробелы и риски
Поле паспорта	Проблема	Что уточнить
Проблема	«Огромный объём данных» и «неэффективность ручной обработки» — это проблема автоматизации отчётности/ETL, а не обязательно ML-прогноза	Разделить: автоматизация подготовки данных + прогноз quantity + визуализация
Пользователь	«Конечный потребитель» не согласуется с прогнозом проданных единиц	Указать роль: менеджер продаж, категорийный менеджер, аналитик, владелец товара
Вход	Нет даты/времени, сезонности, промо, остатков, региона	Если есть дата — добавить; если нет — явно указать, что модель не прогнозирует будущее, а оценивает quantity при заданных признаках
Целевая переменная	Не определена гранулярность: строка чека, товар-день, товар-город-день?	Зафиксировать: «quantity — количество единиц в строке продажи за день/транзакцию»
Разбиение	80/20 случайно может дать утечку будущего или дублей	Если есть время — chronological split / TimeSeriesSplit; если важна генерализация на новые товары — GroupShuffleSplit по product
Baseline	Не сказано, какая базовая модель	DummyRegressor(strategy="median") или mean; для временных данных — naive-прогноз
Категориальные признаки	product, manager, city могут быть высококардинальными	OneHot для низкой кардинальности, TargetEncoder/Ordinal + деревья для высокой; всё внутри Pipeline
Метрики	MSE и RMSE частично дублируются; R² плохо интерпретируется для скошенного quantity	Добавить WAPE/MAPE с оговоркой про нули; смотреть MAE/RMSE в единицах quantity
Ограничения	Предупреждение заявлено, но не формализовано	Сделать фиксированный текст warning в Streamlit и model card
Приёмка	Нет критериев успешности	Задать до старта: например, MAE на test ниже baseline на X%, R² > 0, тесты проходят

Рекомендации по улучшению паспорта
1.	Уточнить бизнес-цель
Не «обработать данные», а «сократить время ручного прогноза/отчётности и дать воспроизводимую оценку quantity с известными ограничениями».
2.	Определить пользователя
Заменить «конечный потребитель» на «менеджер продаж / категорийный менеджер / аналитик». Если нужен именно конечный потребитель, то целевая переменная должна быть другой.
3.	Зафиксировать гранулярность и горизонт
Пример: «прогноз количества единиц товара в строке продажи на следующий день для известного товара, города, менеджера, цены и скидки». Без этого метрики неинтерпретируемы.
4.	Добавить временной признак, если он есть
Для прогноза продаж дата, день недели, месяц, праздники, промо-периоды критичны. Если даты нет — прямо написать: «модель не является прогнозом будущего, это оценка при заданных условиях».
5.	Выбрать стратегию split осознанно
o	есть время → хронологический 80/20 и TimeSeriesSplit в CV;
o	важны новые товары → GroupShuffleSplit по product;
o	обычные i.i.d. данные → train_test_split(random_state=42).
6.	Определить baseline явно
Например: DummyRegressor(strategy="median"). Сравнивать MAE/RMSE/R² модели и baseline. В отчёте показать абсолютное и относительное улучшение.
7.	Строить полный Pipeline
ColumnTransformer + кодирование + масштабирование + модель. Сохранять через joblib весь pipeline, а не только модель. Это защищает от утечек и упрощает Streamlit.
8.	Добавить проверки в pytest
o	схема данных и типы;
o	отсутствие пропусков после preprocessing;
o	загрузка joblib;
o	форма предсказания;
o	метрики не хуже baseline;
o	warning отображается в Streamlit.
9.	Формализовать warning
Пример текста:
«Прогноз основан на исторических данных. Модель не учитывает остатки на складе, конкурентов, сезонность и маркетинговые кампании, если они не были в признаках. Для новых товаров, городов и менеджеров прогноз ненадёжен. Не использовать для автоматических решений без проверки человеком».
10.	Добавить артефакты диплома
README.md, requirements.txt, model.joblib, metrics.json, model_card.md, папка tests/, скрипт обучения, Streamlit-приложение.
